# 对 basic_framework 二次开发的建议

参考仓库：https://github.com/HNUYueLuRM/basic_framework

此 OLED 工程只演示该仓库的 BSP -> module -> application 分层与注册方式，
没有复制整套 RM 应用、消息中心、FreeRTOS 或 PID 控制链。

## 优先修改的边界

1. **分开可复用框架和机器人示例。** 保留 bsp/modules，提供一个最小可构建工程；
   底盘、云台和发射等应用作为独立示例工程。教学用的 oled_demo、uart_demo、
   can_demo 各自有 main、CubeMX 配置和明确源文件列表，不使用例程切换宏。
2. **明确注册和启动顺序。** 设备配置在应用中，模块内部注册所需 BSP；
   先建立实例和回调，再开启对应硬件接收服务。避免接收中断早于对象初始化完成。
   汇总入口只调用各应用初始化；不能把板级选择写死到通用模块。
3. **支持张大头电机协议。** 新增独立 ZDT 模块，提供速度/位置命令及反馈接口。
   CAN 封装支持标准帧和扩展帧，把帧类型、ID、长度和负载一起保存进发送队列。
   张大头驱动器内部负责电机闭环，基础命令例程不强制添加主控 PID；
   底盘位移外环等功能作为额外应用。
4. **统一接口失败语义。** 注册失败不消耗实例；发送队列满、参数错误、超时
   都应有明确返回状态，调用方决定丢弃、重试或进入故障处理。不要默默丢弃协议
   分包帧，也不要无限忙等。采用静态实例池适合教学，不必全盘沿用 malloc。
5. **明确跨任务和中断的数据归属。** 定义回调执行环境、缓冲区有效期、
   发送缓存是否复制；中断只完成必要解析/通知，阻塞处理放到任务。
   消息中心若供不同任务使用，需检查并发安全、队列满的处理与错误返回。
6. **整理构建和文档。** 用 .c 保存函数实现，.h 保存声明；任务函数不在
   robot_task.h 中定义。工具路径、调试器序列号由本地配置提供。
   每个模块配接线、最小调用流程、单位、回调规则和故障排查。

## 当前 GitHub 与本地版本的差异

检查时本地 basic_framework 为 c1394f3，GitHub master 为 1a136eb。
GitHub 新版 CAN 已采用发送队列和邮箱完成中断，接收也会按句柄和 ID 分发。
二开时应选择并记录一个具体基线版本，按源码确认接口，不将旧版调用直接套用到新版。

当前 GitHub CAN 队列仍以标准帧和实例 tx_id 组织发送；接入 ZDT 扩展帧和分包时，
必须同时适配队列元素、发送头和接收匹配方式。

## 与本例程的对应

OLED_Register/IIC_Register 的实现各在其模块内；APP/app_init.c 集中配置和调用，
适用于只有一个应用的新人例程。应用数量增多后，可由统一入口调用
App_Display_Init、App_Chassis_Init 等，各自拥有模块实例，而无需改变底层接口。
